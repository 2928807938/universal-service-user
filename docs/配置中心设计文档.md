# 通用服务配置中心设计文档

## 一、概述

### 1.1 背景与目标

通用服务配置中心旨在为多租户用户提供统一的配置管理解决方案。用户只需编写配置文件并使用配置工具上传到数据库，服务会自动从数据库加载配置，实现配置的集中化管理和版本控制。

### 1.2 核心价值

- **简化用户操作**：用户只需维护本地配置文件，无需手动调用上传接口
- **统一配置管理**：所有配置存储在中心数据库，便于管理和审计
- **多租户隔离**：每个用户拥有独立的租户ID，配置完全隔离
- **版本控制**：自动记录配置变更历史，支持版本回溯

### 2.3 关键概念说明

为了更好地理解配置中心的工作原理，需要明确以下关键概念：

#### 配置存储位置

| 位置 | 类型 | 谁控制 | 用途 |
|------|------|--------|------|
| **config.yaml** | 本地文件 | 用户 | 配置编辑、版本控制 |
| **数据库** | 远程存储 | universal-service | 配置存储、版本管理、多实例同步 |
| **服务缓存** | 内存 | 服务自动 | 性能优化、快速访问 |

#### 数据流向

```
config.yaml  →[universal-service]→  数据库  →[服务]→  内存缓存
   ↑              (上传)           (存储)      (加载)    (使用)
  用户
```

#### 关键要点

1. **配置文件 ≠ 运行时配置**
   - `config.yaml` 只是配置的"编辑版本"
   - 数据库中的配置才是"真实来源"
   - 服务缓存只是"性能优化"

2. **上传配置 ≠ 加载配置**
   - 上传配置：用户手动操作，把配置存到数据库
   - 加载配置：服务自动操作，从数据库读配置到内存
   - 两者是独立的操作，通过配置变更通知关联

3. **服务不需要重启**
   - 配置更新后，服务通过监听机制自动感知
   - 清除缓存后，下次请求时自动加载新配置
   - 整个过程对用户透明

4. **单一数据源原则**
   - 所有服务实例都从同一个数据库读取配置
   - 避免配置不一致问题
   - 实现多实例配置同步

## 三、用户使用流程

### 3.1 应用注册（一次性）

**流程说明**：
1. 用户调用通用服务的应用注册接口
2. 提供应用基本信息（应用名称、描述等）
3. 系统生成唯一的租户ID（tenant_id）
4. 将应用信息存储到数据库
5. 返回 tenant_id

**注意事项**：
- tenant_id 是租户的唯一标识符
- 建议使用有意义的标识符（如 company_name 或 UUID）
- tenant_id 用于配置隔离和数据隔离

### 3.2 编写配置文件

**配置文件结构**：
- 租户标识区：tenant_id、environment
- 数据库配置区：连接信息、连接池参数
- 缓存配置区：Redis 连接信息
- 业务配置区：JWT、邮件、短信等
- 服务配置区：端口、运行模式等

**配置文件示例**：
```yaml
app:
  tenant_id: "tenant_001"  # 或使用 UUID
  environment: "prod"  # 使用缩写，也可以写 production

database:
  host: "localhost"
  port: 5432
  # ...

redis:
  host: "localhost"
  port: 6379
  # ...
```

**环境标识说明**：
- 开发环境可使用：`dev` 或 `development`
- 测试环境可使用：`test` 或 `testing`
- 生产环境可使用：`prod` 或 `production`
- 预发布环境可使用：`staging` 或 `pre`

### 3.3 配置管理方式

通用服务自身提供配置管理功能，通过命令行参数控制不同模式：

#### 服务运行模式

**1. 服务模式（默认，长期运行）**
```bash
universal-service --config config.yaml
```
- 启动服务进程
- 监听业务请求
- 从数据库加载配置
- 由 systemd/supervisor/Docker 管理

**2. 配置管理模式（执行后退出）**
```bash
universal-service --config config.yaml --upload-only
```
或简写：
```bash
universal-service -c config.yaml -u
```
- 上传配置到数据库
- 不启动服务进程
- 执行完成后退出

#### 功能说明

**配置管理模式**：
- ✅ 验证配置文件格式
- ✅ 上传配置到数据库
- ✅ 查看配置版本和历史
- ✅ 对比配置差异
- ✅ 回滚配置
- ✅ 不涉及服务启动/重启

#### 优势

**单一程序，多功能**：
- 减少部署复杂度
- 代码复用，减少维护成本
- 版本自动同步
- 统一的配置验证逻辑

### 3.4 上传配置

**上传命令**：
```bash
universal-service --config config.yaml --upload-only
```

**简写形式**：
```bash
universal-service -c config.yaml -u
```

**使用场景**：
当用户需要修改配置时：
1. 编辑 `config.yaml` 文件
2. 执行上传命令
3. 配置自动同步到数据库
4. 运行中的服务自动刷新缓存（无需重启）

**上传流程**：
1. 读取并解析配置文件
2. 验证配置完整性（tenant_id、必填字段等）
3. 连接中心数据库
4. 验证 tenant_id 是否存在
5. 上传配置到数据库（版本号自动递增）
6. 记录配置变更历史
7. 通知服务刷新配置缓存
8. 退出

**日志输出示例**：
```
[INFO] 📤 开始上传配置到数据库...
[INFO] 📄 配置文件: config.yaml
[INFO] ✅ 配置验证通过
[INFO] ✅ 租户ID验证通过: tenant_001
[INFO] 📝 更新配置，版本号: 2 -> 3
[INFO] ✅ 配置上传成功！
[INFO]    租户ID: tenant_001
[INFO]    环境: prod
[INFO]    版本号: 3
[INFO] ✅ 已通知服务刷新配置

🎉 配置上传完成！服务将在下次请求时自动使用新配置。
```

**命令行参数说明**：
- `--config` / `-c`：指定配置文件路径（必需）
- `--upload-only` / `-u`：配置管理模式，执行后退出（必需）
- `--help` / `-h`：显示帮助信息（可选）

## 四、数据库设计

### 4.1 应用表 (apps)

**字段说明**：
- `id`: 主键
- `tenant_id`: 租户唯一标识（对外暴露）
- `app_name`: 应用名称
- `description`: 应用描述
- `status`: 应用状态（active/inactive）
- `created_at`: 创建时间
- `updated_at`: 更新时间

**索引**：
- 主键索引：id
- 唯一索引：tenant_id

### 4.2 配置表 (app_configs)

**字段说明**：
- `id`: 主键
- `tenant_id`: 关联租户ID
- `environment`: 环境标识（dev/test/prod）
- `config_data`: 完整配置的JSON数据
- `version`: 配置版本号
- `created_at`: 创建时间
- `updated_at`: 更新时间

**索引**：
- 主键索引：id
- 唯一索引：(tenant_id, environment)
- 普通索引：tenant_id

### 4.3 配置变更历史表 (config_history)

**字段说明**：
- `id`: 主键
- `tenant_id`: 租户ID
- `old_config`: 变更前的配置（JSON）
- `new_config`: 变更后的配置（JSON）
- `version`: 版本号
- `changed_by`: 变更人
- `change_reason`: 变更原因
- `created_at`: 创建时间

**索引**：
- 主键索引：id
- 普通索引：tenant_id、created_at

## 五、API 接口设计

### 5.1 应用管理接口

#### 用户注册
- **路径**: `POST /api/v1/apps/register`
- **功能**: 注册新应用，获取 tenant_id
- **请求参数**:
  - app_name: 应用名称（必填）
  - description: 应用描述（选填）
  - email: 联系邮箱（选填）
- **返回数据**:
  - tenant_id: 租户唯一标识
  - app_name: 应用名称
  - created_at: 创建时间

#### 查看应用信息
- **路径**: `GET /api/v1/apps/:tenant_id`
- **功能**: 查询应用基本信息
- **返回数据**:
  - tenant_id、app_name、description、status 等

### 5.2 配置管理接口

#### 更新配置（配置管理工具）
- **命令**: `universal-service --config config.yaml upload`
- **功能**: 上传配置到数据库，触发服务刷新
- **参数说明**:
  - `--config`: 配置文件路径（必需）
  - `upload`: 上传子命令（必需）
- **执行效果**:
  - 配置上传到数据库，版本号自动递增
  - 记录配置变更历史
  - 自动通知服务刷新缓存
  - 服务无需重启即可使用新配置


### 5.3 业务接口

所有业务接口都需要在请求头中携带租户标识：
- `X-Tenant-Id`: 租户ID
- `X-App-Environment`: 环境标识（选填）

**示例接口**：
- 用户注册: `POST /api/v1/user/register`
- 用户登录: `POST /api/v1/user/login`
- 密码重置: `POST /api/v1/user/reset-password`

## 六、认证与安全

### 6.1 租户标识机制

**标识流程**：
1. 客户端请求携带 tenant_id
2. 服务器根据 tenant_id 查询租户信息
3. 验证 tenant_id 有效性
4. 验证通过后加载数据库配置
5. 验证失败返回 404 错误

**tenant_id 管理建议**：
- 使用有意义的标识符（如公司名、项目名）
- 或使用 UUID 保证唯一性
- 建议将 tenant_id 纳入配置文件管理

### 6.2 租户隔离

**隔离级别**：
- 数据隔离：不同 tenant_id 的配置完全分离
- 资源隔离：每个租户拥有独立的数据库连接池
- 权限隔离：只能访问自己 tenant_id 下的数据和配置

### 6.3 敏感信息保护

**加密建议**：
- 数据库密码使用 AES-256 加密存储
- 日志输出时自动脱敏（密码、密钥等）
- 支持配置字段级别的加密标记
- 使用 HTTPS 传输敏感数据

## 七、配置加载与缓存机制

### 7.1 配置管理的两个关键操作

**重要说明**：配置管理包含两个独立但相关的操作，需要清楚区分：

#### 1. 上传配置（用户操作）

**执行者**：用户
**工具**：`universal-service`
**作用**：把配置存储到数据库
**时机**：用户修改配置后手动执行

**流程**：
```
用户编辑 config.yaml
     ↓
执行 universal-service upload
     ↓
配置存储到数据库
     ↓
版本号自动递增
     ↓
发送配置变更通知
```

**结果**：
- ✅ 配保存在 `app_configs` 表中
- ✅ 版本号递增
- ✅ 记录到 `config_history` 表
- ❌ **此时服务还未使用新配置**

---

#### 2. 加载配置（服务自动）

**执行者**：通用服务
**方式**：从数据库读取
**作用**：把配置加载到内存缓存
**时机**：
- 服务启动时
- 收到配置变更通知后
- 业务请求需要时

**流程**：
```
服务收到通知（或启动）
     ↓
从数据库读取配置
     ↓
解析配置数据
     ↓
创建连接池
     ↓
存入内存缓存
     ↓
业务逻辑使用
```

**结果**：
- ✅ 配置加载到内存
- ✅ 连接池创建完成
- ✅ 后续请求直接使用缓存

### 7.3 缓存工作原理：第一次 vs 后续请求

**核心价值**：配置缓存机制的主要作用是避免重复加载配置和重复创建资源池，从而大幅提升性能。

#### 7.3.1 第一次请求（缓存未命中）

当某个租户的配置首次被访问时，系统需要完整的加载流程：

```
┌─────────────────────────────────────────────────────────────┐
│                 第一次请求处理流程                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 客户端请求                                               │
│     POST /api/v1/user/register                              │
│     Headers: X-Tenant-Id: tenant_001                        │
│                                                             │
│     ↓                                                       │
│                                                             │
│  2. 检查内存缓存                                             │
│     Key: "tenant_001:prod"                                  │
│     结果: ❌ 未找到                                         │
│                                                             │
│     ↓                                                       │
│                                                             │
│  3. 查询数据库                                               │
│     SELECT * FROM app_configs                               │
│     WHERE tenant_id = 'tenant_001' AND environment = 'prod' │
│     耗时: ~20ms                                             │
│                                                             │
│     ↓                                                       │
│                                                             │
│  4. 解析配置数据                                             │
│     - 数据库连接参数                                         │
│     - Redis 连接参数                                         │
│     - JWT 密钥等                                            │
│     耗时: ~1ms                                              │
│                                                             │
│     ↓                                                       │
│                                                             │
│  5. 创建数据库连接池                                         │
│     - 建立 TCP 连接                                         │
│     - 认证数据库用户                                         │
│     - 初始化连接池（max_open_conns=100）                     │
│     耗时: ~30ms                                             │
│                                                             │
│     ↓                                                       │
│                                                             │
│  6. 创建 Redis 连接                                          │
│     - 建立 Redis 连接                                       │
│     初始化连接池                                             │
│     耗时: ~5ms                                              │
│                                                             │
│     ↓                                                       │
│                                                             │
│  7. 存入内存缓存                                             │
│     cache.Store("tenant_001:prod", CachedConfig{           │
│         Config: config,                                     │
```

- **创建**：第一次请求时自动创建
- **复用**：后续请求持续复用，无需重新加载

- **隔离**：不同租户的配置完全独立缓存

**关键特性**：

1. **完全隔离**
   - 租户A和租户B的配置独立存储
   - 租户A和租户B的连接池完全独立
   - 租户A的配置更新不影响租户B

2. **并行加载**
   - 不同租户的加载过程可以并行执行
   - 使用租户级别的锁，而非全局锁
   - 互不阻塞，提升并发性能

3. **独立缓存Key**
   - Key格式: `"{tenantID}:{environment}"`
   - `tenant_001:prod` vs `tenant_002:prod`
   - 不同租户永远不会冲突

4. **资源隔离**
   ```
   租户A的连接池:
     - 连接到: database_a
     - 用户: user_a
     - 连接数: 100

   租户B的连接池:
     - 连接到: database_b  (完全不同的数据库)
     - 用户: user_b
     - 连接数: 50
   ```

**并发安全保障机制**：

```go
// 伪代码示例
func GetConfig(tenantID, env string) (*CachedConfig, error) {
    cacheKey := tenantID + ":" + env

    // 1. 先检查缓存（无锁，快速）
    if cached, ok := cache.Load(cacheKey); ok {
        return cached.(*CachedConfig), nil
    }

    // 2. 获取租户级别的锁（不同租户不会互相阻塞）
    lockKey := "lock:" + cacheKey
    mu.Lock(lockKey)
    defer mu.Unlock(lockKey)

    // 3. 双重检查（防止等待锁期间其他协程已加载）
    if cached, ok := cache.Load(cacheKey); ok {
        return cached.(*CachedConfig), nil
    }

    // 4. 从数据库加载配置
    config := loadFromDB(tenantID, env)

    // 5. 创建租户独立的连接池
    pool := createConnectionPool(config.Database)

    // 6. 存入缓存
    cached := &CachedConfig{
        Config: config,
        Pool:   pool,
    }
    cache.Store(cacheKey, cached)

    return cached, nil
}
```

### 7.4 多级缓存架构

```
┌─────────────────────────────────────────────────────┐
│              三级缓存架构                            │
├─────────────────────────────────────────────────────┤
│                                                     │
│  L1: 内存缓存 (sync.Map)                            │
│  ┌─────────────────────────────────────────┐       │
│  │ map[tenantID + env] *CachedConfig       │       │
│  │ - 配置数据                               │       │
│  │ - 数据库连接池                           │       │
│  │ - Redis连接池                            │       │
│  │ - 版本号                                 │       │
│  │ - 过期时间（默认5分钟）                  │       │
│  └─────────────────────────────────────────┘       │
│           ↓ 缓存未命中                               │
│  L2: 数据库配置表 (app_configs)                     │
│  ┌─────────���───────────────────────────────┐       │
│  │ SELECT * FROM app_configs               │       │
│  │ WHERE tenant_id = ? AND environment = ? │       │
│  └─────────────────────────────────────────┘       │
│           ↓ 降级场景                                 │
│  L3: 本地配置文件 (config.yaml)                     │
│  ┌─────────────────────────────────────────┐       │
│  │ 启动时读取的本地配置                     │       │
│  └──��──────────────────────────────────────┘       │
└─────────────────────────────────────────────────────┘
```

**缓存工作流程**：
1. **首次请求**：从数据库加载配置 → 创建连接池 → 存入内存缓存
2. **后续请求**：直接从内存缓存获取 → 复用连接池 → 快速响应
3. **缓存过期**：自动删除 → 下次请求重新加载
4. **配置更新**：主动清除缓存 → 下次请求加载新版本

**并发安全保障**：
- 使用 `sync.Map` 实现线程安全的缓存
- 双重检查锁定（Double-Checked Locking）防止并发重复加载
- 连接池复用，避免重复创建资源

### 7.3 配置刷新机制

服务启动后会自动监听配置变更，支持以下刷新策略：

**方案一：数据库事件监听（推荐，实时）**

适用场景：PostgreSQL 数据库

工作原理：
1. 数据库配置表创建触发器
2. 配置更新时触发 `pg_notify` 通知
3. 服务实时收到通知
4. 清除对应租户的缓存
5. 下次请求自动加载新配置

数据库触发器：
```sql
CREATE OR REPLACE FUNCTION notify_config_update()
RETURNS TRIGGER AS $$
BEGIN
    PERFORM pg_notify(
        'config_update_channel',
        json_build_object(
            'tenant_id', NEW.tenant_id,
            'environment', NEW.environment
        )::text
    );
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER config_update_trigger
AFTER INSERT OR UPDATE ON app_configs
FOR EACH ROW
EXECUTE FUNCTION notify_config_update();
```

**方案二：定时轮询（备份，兜底）**

工作原理：
1. 后台定时任务每5分钟检查一次
2. 对比缓存中的版本号和数据库中的版本号
3. 版本号不一致则刷新缓存

**方案三：主动推送通知（手动触发）**

用户执行 `universal-service` 命令时：
1. 配置上传到数据库成功
2. 自动调用服务内部通知接口
3. 服务清除对应租户的缓存

- 不要在配置文件中明文存储密码
- 使用最小权限原则配置数据库访问

### 12.2 开发侧最佳实践

**代码组织**：
- 配置管理模块独立

**错误处理**：
- 详细的错误日志
- 友好的错误提示
- 降级机制保证服务可用性（缓存失败 → 数据库 → 本地配置）
